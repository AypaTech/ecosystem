# Design decisions and deviations from SPEC.md

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-09-22 | Target **Odoo 19.0** instead of 18.0 (SPEC §2). | Owner decision. The ecosystem repo is on branch `20` and its Docker image runs 20.0; owner chose 19.0 as the first target. All APIs were verified against `odoo/odoo@19.0`. |
| 2026-09-22 | Core module technical name is **`aypatech_telegram_connector`** (SPEC: `telegram_discuss`). Bridges: `aypatech_telegram_connector_crm`, `_sale`, `_helpdesk` (Enterprise `helpdesk`) and `_aypatech_helpdesk` (ecosystem's own helpdesk), as sibling folders of the ecosystem repo. | The ecosystem Dockerfile only adds top-level folders that contain a `__manifest__.py`; this repo folder therefore *is* the core module. Model names (`telegram.*`) and field names follow SPEC unchanged. |
| 2026-09-22 | Two helpdesk bridges instead of one. | Owner asked for both Enterprise `helpdesk` and `aypatech_helpdesk`. The Enterprise one is written against the public 19.0 `helpdesk.ticket` API without access to its source and must be verified on an Enterprise instance. |
| 2026-09-22 | License OPL-1 on all modules. | Owner confirmed SPEC §2. |
| 2026-09-22 | `telegram.bot.polling_offset` is a **Char** (SPEC: Integer). | Odoo `Integer` is int4; Telegram `update_id` is not guaranteed to fit. Helpers `_get_polling_offset()` / `_set_polling_offset()` convert. |
| 2026-09-22 | `telegram.update.update_id`, all chat/user/message ids are `Char`. Inbox is processed in `id` order (insertion order), not by `update_id`. | Char sorts lexically; insertion order equals Telegram order for both webhook and polling. |
| 2026-09-22 | Outbound hook = `discuss.channel._message_post_after_hook` (SPEC suggests `message_post`). | Narrowest hook that has the final `mail.message` (`is_internal`, `subtype_id`, attachments). See `DISCUSS_NOTES.md` §3. |
| 2026-09-22 | `discuss.channel.telegram_conversation_id` (stored Many2one) added. | Needed by the record rules that let team members/managers read telegram channels they are not a member of. |
| 2026-09-22 | Conversations without a team are visible to every Telegram user of the company. | Otherwise unrouted conversations would be invisible to everybody except managers. |
| 2026-09-22 | One `telegram.delivery` per `telegram.message`; a delivery has *parts* (text chunks, attachments). `parts_sent` is committed after each part so a retry never re-sends a part Telegram already accepted. Extra Telegram message ids are kept in `telegram.message.extra_telegram_message_ids`. | Idempotent retries with split text/captions. |
| 2026-09-22 | Queue claim selects only the **head** delivery of each conversation (`NOT EXISTS` an older delivery in `queued/sending/failed_retryable`) with `FOR UPDATE SKIP LOCKED`, then sets `sending` and commits before any HTTP call. | Guarantees per-conversation ordering (SPEC §9.4) and at-most-one worker per delivery. |
| 2026-09-22 | Deliveries of a bot with `auth_failed = True` are not claimed until a successful `getMe` clears the flag. | SPEC §12 "auth: stop all deliveries for the bot". |
| 2026-09-22 | Telegram API calls from buttons/wizard (getMe, setWebhook, deleteWebhook, getWebhookInfo) run in the request. | They create no business data; nothing can become a "ghost" message. Outbound messages always go through the queue. |
| 2026-09-22 | Commits inside services are skipped while tests run (`odoo.modules.module.current_test`), same technique as core `mail.mail`. | Test cursors forbid `commit()`. |
| 2026-09-22 | Dashboard is a kanban view on `telegram.bot` with computed counters. | SPEC §17 allows it; no extra OWL code to port. |
| 2026-09-22 | `/start` welcome/privacy messages are queued as outbound `telegram.message` authored by OdooBot, posted in the channel (so agents see what the customer received). | Keeps "never call the API in the creating transaction" and gives a visible trace. |
| 2026-09-22 | Unassigned new conversations add the team members (or, without team, the Telegram managers of the company) as channel members. | Non-`channel` Discuss types are only listed for pinned members; without this nobody would see a new unassigned chat in Discuss. |
| 2026-09-22 | Bridges are `auto_install: True`. | Each installs by itself as soon as its target app is present; the core never depends on them (SPEC §20 Phase 6). |
| 2026-09-22 | `aypatech_telegram_connector_aypatech_helpdesk` uses `aypatech_ticket_id` / `action_create_aypatech_ticket` (not `ticket_id`). | Both helpdesk bridges can be installed in the same database without a field clash. |
| 2026-09-22 | **Known blocker:** `aypatech_helpdesk` is an Odoo 20.0 module (`security/ir.access.csv` uses the 20.0 `operation/domain` format), while this connector targets 19.0. | Its bridge can only be installed once both run on the same Odoo version (backport `aypatech_helpdesk` to 19.0, or port the connector to 20.0). |
| 2026-09-22 | Helpdesk (Enterprise) bridge written without the Enterprise source. | Uses only `helpdesk.ticket` fields present in every recent version (`name, partner_id, user_id, company_id, description`) and the view `helpdesk.helpdesk_ticket_view_form` / group `helpdesk.group_helpdesk_user`; verify on an Enterprise 19.0 instance. |
| 2026-09-22 | Ticket replies are forwarded by posting a copy in the Telegram channel (not by calling the queue directly). | One outbound path: same queue, retries, status indicator and agent-visible history. |
| 2026-09-25 | Bridge modules merged into `aypatech_telegram_connector` (one product). CRM and Sales become hard dependencies. | Helpdesk stays optional: `ticket_ref` (Reference field, selection = installed helpdesk models, Enterprise first) + a `mail.thread._message_post_after_hook` override that forwards replies only for helpdesk ticket models. No field or view is added on the ticket model, so the module installs with either helpdesk or none. |
